## Таблица `dim_goods_scd2`

Те же поля, что в `dim_goods`, плюс три служебных:

| Поле | Смысл |
|------|-------|
| `valid_from` | с какой даты действует версия |
| `valid_to` | по какую дату; у текущей версии `9999-12-31` |
| `is_current` | `TRUE` только у актуальной версии |

Для текущей версии вместо `NULL` стоит `9999-12-31`, чтобы условие `valid_from <= дата < valid_to` работало без отдельной проверки на `NULL`.

## Демо смены атрибута

Товар `sku_id = 14224` «Кофе Makfa 500 г v8»:

1. Все товары из `dim_goods` записываются первой версией: действуют с `2024-01-01`, `is_current = TRUE`.
2. С 1 июля 2024 кофе переносят из отдела «Бакалея» в «Напитки»: `UPDATE` закрывает старую версию (`valid_to = 2024-07-01`, `is_current = FALSE`).
3. `INSERT` добавляет новую текущую версию с `dept = 'Напитки'`, `valid_from = 2024-07-01`.

Запрос «Вывод 1» показывает **две версии** этого товара.

## Как факт попадает в нужную версию

Строка чека соединяется с той версией товара, которая действовала на дату продажи:

```sql
JOIN dim_goods_scd2 v
  ON v.sku_id = f.sku_id
 AND CAST(f.sold_at AS DATE) >= v.valid_from
 AND CAST(f.sold_at AS DATE) <  v.valid_to
```

Упрощение: версия выбирается по дате продажи при запросе, а не записывается ключом версии в факт при загрузке.

У этого кофе 6 продаж: 3 до июля (1 015.80) остаются в «Бакалее», 3 после (1 503.05) попадают в «Напитки» — «Вывод 2».  
«Вывод 3» проверяет, что через SCD2 выручка сети не потерялась и не задвоилась: 15 383 068.36, как в P05.
