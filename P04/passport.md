## 1. Бизнес-цель витрины

Витрина собирает продажи сети из 12 магазинов за 2024 год: выручку, объём продаж в штуках и килограммах, разрез по отделам, производителям, магазинам, клиентам и способам оплаты. Она помогает понять, какие отделы и магазины приносят больше денег, как работает программа лояльности и как покупатели предпочитают платить.

---

## 2. Grain

**Одна строка факта = одна строка чека** (один товар, проданный в один момент одному клиенту в одном магазине).

---

## 3. Fact-таблица

| Имя | Grain | Примечание |
|-----|-------|------------|
| `fact_receipt_line` | одна строка = одна строка чека, ключ `receipt_line_id` | В сырье `fact_receipt.csv` `receipt_line_id` уникален (25 000 строк, дублей нет). Номера самого чека в сырье нет, поэтому строки нельзя собрать в «один чек» — grain остаётся «строка чека». |

---

## 4. Меры

| Мера | Тип (sum ok / нет) | Определение |
|------|--------------------|-------------|
| `line_total` | sum ok | Выручка по строке = `qty * sell_price` (в сырье уже посчитано; расхождение не больше 1 копейки — проверено на P03). |
| `qty` | sum ok, но только внутри одной единицы | Количество: для `шт` — штуки, для `кг` — вес. Складывать штуки с килограммами нельзя — суммируем с фильтром по `measure_unit`. |
| `sell_price` | sum нет | Фактическая цена за единицу; считаем среднюю (`SUM(line_total)/SUM(qty)`), min/max. |
| `discount_amount` | sum ok (расчётная) | Скидка = `(list_price - sell_price) * qty`; берётся из факта + `dim_goods`. |
| `lines_cnt` | sum ok (count) | Число строк чека: `COUNT(*)`. |

## 6. Три бизнес-вопроса → запросы в `sql/analytics.sql`

| № | Вопрос | Запрос | Что в SQL |
|---|--------|--------|-----------|
| 1 | Какой отдел дал наибольшую выручку в каждом квартале 2024 года? | «Вопрос 1» | `GROUP BY` + окна `RANK() OVER (PARTITION BY quarter)` и доля `SUM() OVER (PARTITION BY quarter)` |
| 2 | Сколько выручки приходится на клиентов с картой лояльности и без неё, по магазинам? | «Вопрос 2» | `GROUP BY` по магазину + `SUM() FILTER` |
| 3 | Как меняется доля оплат через СБП по месяцам? | «Вопрос 3» | `GROUP BY` по месяцу + окно `LAG()` (изменение к прошлому месяцу) |

**Короткие ответы (по `analytics_output.txt`):**

1. В I квартале лидер — «Бытовая химия» (22.3 % выручки квартала), во II–IV — «Мясо и птица» (≈ 21.4 %).
2. Клиенты с картой лояльности дают около 60 % выручки в каждом магазине (от 58.4 % в магазине №9 до 61.5 % в №2).
3. Доля СБП держится в коридоре 16–18.5 % строк чека: минимум в январе (16.1 %), максимум в октябре (18.4 %).

## 7. Эталонный SQL главной метрики

**Главная метрика: выручка сети** = `SUM(line_total)` по `fact_receipt_line`.  
Возвратов в сырье нет, поэтому выручка = сумма всех продаж.

```sql
-- sql/canonical_metric.sql
SELECT SUM(line_total) AS revenue
FROM fact_receipt_line;
```

**Зафиксированное значение:** `15 383 068.36 ₽` (совпадает с P01 и P03).  
Это число должно совпасть с карточкой на дашборде (З11).

## 8. Риски / cut

- **Нет номера чека** — есть только `receipt_line_id`, поэтому настоящий «средний чек» не посчитать; считаем среднюю сумму строки.
- **Нет справочника магазинов** — в факте только `shop_id` 1–12; `dim_shop` собираем из факта.
- **Штуки и кг в одном поле `qty`** — суммировать можно только по одной единице измерения.
- **Цена только текущая** — `list_price` без истории; для SCD2 нужны `valid_from` / `valid_to`.
- **Возвратов нет** — отрицательных `qty` и `line_total` в сырье нет, выручка = продажи.
- **ClickHouse-кластер / Kafka / ML** — не делаем, подробности в `cut.md`.
